## 6. Known parity risks and findings

### A. Route coverage is strong, but not sufficient

All 20 sitemap URLs have corresponding local routes. This is a positive baseline. The generic `[slug]` service route requires validation that every sitemap slug resolves correctly and renders complete content.

### B. Service navigation may not expose every live service route

`Header.tsx` builds desktop service navigation from `navServices`, which is derived from all `serviceCards`. The data contains the 11 service cards, including Room Additions and Basement Remodeling. However, the live `/services/` text inventory clearly shows 9 visible service categories and the sitemap exposes 11 detail routes. v3.2 must explicitly verify that all live service links are reachable from navigation or the services index without relying only on a sitemap.

### C. Location navigation intentionally filters Richmond

`Header.tsx` excludes location records whose `href` is `#`. Richmond is represented with `href: "#"`, so the header's location dropdown does not show Richmond as a destination. The live site presents Richmond as a service area. v3.2 must resolve whether Richmond should link to the homepage, areas hub, or a dedicated `/richmond-tx/` page; do not invent a route without a source/approval.

### D. Mobile navigation does not list individual locations

The desktop `More` menu lists individual locations, but the mobile menu lists only `Areas We Serve` and FAQs. This is a presentation/visibility gap, especially given the requirement not to truncate service areas. v3.2 should make all service areas discoverable on mobile, either through the areas page or an expanded mobile submenu.

### E. Existing local content is not automatically live-copy parity

The local data contains polished/restructured copy, including additional explanatory sections and FAQs. That may be valid redesign content, but it cannot be assumed to be identical to the live source. Every meaningful factual claim, service list, location, heading, and FAQ must be classified as:

- Exact live-source copy
- Faithful restructuring
- New approved copy
- Unsupported/invented copy
- Missing live content

### F. Claims require source verification

The local code uses claims such as “35+ years,” “over 35 years of combined experience,” and “since 2007.” These appear in live metadata/content, but v3.2 should centralize and verify them so variants do not conflict. The current local location data also includes a Richmond description mentioning “35+ years of experience,” while the live page wording and metadata need to be treated as the authority for exact phrasing.

### G. FAQ parity is unresolved

The local FAQ data has 15 entries. The scraped live FAQ text exposes only the page heading because the accordion content is likely rendered or hidden in a way the simple scraper does not capture. This requires a browser/DOM or source-level extraction pass before declaring parity. No FAQ should be removed merely because the first scrape did not expose it.

### H. Asset parity is unresolved

The local project has reconstructed/localized assets under `public/images/`. The live site uses WordPress assets, including hero images, maps, logos, icons, and footer graphics. v3.2 must verify visual/content equivalence where an asset communicates factual meaning, especially logos, maps, project galleries, and service imagery.

### I. The deployed v3.1 sitemap check needs attention

Fetching `https://nws-v31.vercel.app/sitemap.xml` returned a 404 during discovery. The local README lists a sitemap route, so deployment behavior and the actual generated sitemap URL need verification before v3.2 release. This is a release/SEO risk, not proof that all local routes are missing.
