# NWS v3.2 Execution Plan

## Mission

Build NWS v3.2 from the local v3.1 project by applying the current client site's complete, verified, meaningful content and copy to the existing v3.1 visual design and technical foundation.

```text
www.nws-homes.com = factual content and URL source of truth
local v3.1         = visual design, components, architecture, and deployment baseline
v3.2               = v3.1 presentation with complete verified client-site content parity
```

## Definition of done

V3.2 is complete only when:

- Every authoritative production URL has a working local/deployed equivalent.
- Every meaningful production page section, service, area, list, CTA, fact, FAQ, and contact detail is present or intentionally represented in the redesign.
- No meaningful content is silently truncated or omitted.
- No unsupported claims, invented services, invented areas, or changed business facts remain.
- Content can be reorganized into the v3.1 design without changing its meaning.
- All nine service areas are discoverable on desktop and mobile.
- All eleven service detail routes are discoverable.
- Contact details and promotional language are consistent.
- Metadata, sitemap, internal links, canonical paths, and route behavior are verified.
- The final site passes route, build, type, lint, content-parity, responsive, and browser checks.

## Hard rules

1. Do not pull from `thela-media-group/nws-homes.com`.
2. Do not replace the local v3.1 architecture.
3. Use the current client site as the factual content source of truth.
4. Preserve meaningful production copy word-for-word where practical, especially facts, lists, service names, area names, claims, FAQs, CTAs, and metadata.
5. Reorganizing content into cards, accordions, sections, or responsive layouts is allowed only when no meaning or required information is lost.
6. Do not invent copy, claims, testimonials, locations, addresses, services, or URLs.
7. Do not remove content to make the design cleaner or shorter.
8. Do not mark parity complete based only on route existence or a heuristic score.
9. Every stage must leave durable evidence in `docs/` or `SCRATCH/` and must pass its own verification before the next stage.
10. Preserve the clean v3.1 baseline and keep v3.2 work reviewable in small slices.

## Stage gates

Each stage has a gate. Do not advance if its gate fails.

| Stage | Objective | Gate |
|---|---|---|
| 0 | Freeze baseline and evidence | Baseline commit, routes, and deployment recorded; working tree understood |
| 1 | Build authoritative content corpus | Every production URL has captured source material and provenance |
| 2 | Build route/content parity matrix | Every production item is classified as exact, restructured, missing, unsupported, or needs decision |
| 3 | Normalize shared facts and information architecture | One canonical source for business facts, services, areas, links, and metadata |
| 4 | Apply global shell and navigation parity | All services/areas are discoverable on desktop/mobile without design regression |
| 5 | Apply page content parity | Page groups meet their acceptance rows with no material omissions |
| 6 | Resolve assets, FAQs, forms, metadata, and SEO | Supporting content and release-critical behavior are verified |
| 7 | Final parity and release audit | All checks pass against the approved matrix; only then call v3.2 complete |

# Stage 2 — Build the parity matrix

## Outcome

Turn the corpus into the implementation contract: nothing important can be forgotten, and every difference has a disposition.

## Work

For every production route and content unit, compare against local v3.1 and classify:

- Exact match
- Same meaning, structurally reorganized
- Local copy differs but is client-approved/unsupported status unknown
- Missing locally
- Local-only unsupported content
- Wrong or inconsistent fact/link
- Asset mismatch
- Needs client decision

Include a row for:

- Every page and service route
- Every H1/H2/content section
- Every service and sub-service
- Every service area
- Every CTA and contact fact
- Every FAQ
- Every navigation link
- Every metadata field
- Every meaningful image/asset

## Evidence

- `docs/v3.2-content-parity-matrix.md`
- `docs/v3.2-content-decisions.md` for unresolved questions
- A summary of omissions and unsupported local additions

## Gate

Every authoritative content item has a classification and required action. No implementation work starts for an unresolved critical item.

### Queue prompt 2

```text
V3.2 STAGE 2 — Build the content parity matrix.

Read docs/v3.2-situation-map.md and docs/v3.2-content-corpus/. Compare the client source corpus against the local v3.1 source without changing application code.

Create docs/v3.2-content-parity-matrix.md. Include every production route, heading/section, paragraph/list, service, area, CTA, contact fact, FAQ, navigation link, metadata field, and meaningful asset. For each row record the live source, local source, parity classification, exact gap, required v3.2 action, and verification method.

Classify items as exact, faithful restructuring, differing/needs review, missing, unsupported local addition, wrong link/fact, asset mismatch, or decision required. Do not hide differences under a heuristic pass. Finish with a prioritized implementation backlog and unresolved decisions. Do not implement code.
```

# Stage 3 — Normalize shared facts and information architecture

## Outcome

Create one canonical local data model so contact facts, service names, service-area names, links, claims, and metadata cannot drift across pages.

## Work

After matrix review:

- Centralize approved business/contact facts.
- Centralize approved claims and offer wording.
- Centralize the authoritative service registry and route mapping.
- Centralize the authoritative service-area registry and route mapping.
- Define gallery and FAQ registries.
- Define canonical metadata and page-title rules.
- Preserve existing route paths unless the matrix explicitly requires a redirect/decision.
- Add structural tests for unique slugs, complete route coverage, valid internal links, and required facts.

Do not rewrite page copy in this stage except where required to remove duplication or establish canonical shared facts.

## Gate

A machine-checkable registry covers all authoritative services, areas, routes, and shared facts, and tests fail if a required item disappears or duplicates conflict.

### Queue prompt 3

```text
V3.2 STAGE 3 — Normalize the approved information architecture.

Use docs/v3.2-content-parity-matrix.md as the contract. Implement only the shared data/model changes needed to create one canonical source for approved business facts, claims, offers, service names/slugs/routes, service areas/routes, galleries, FAQs, and metadata rules.

Preserve the v3.1 visual design and existing URLs. Do not do broad page redesign in this stage. Add real structural tests for complete route coverage, unique slugs, valid internal links, all nine service areas, all eleven service detail routes, and consistent contact facts. Run targeted tests, typecheck, lint, and build. Update the matrix with evidence and stop if any critical source decision is unresolved.
```

# Stage 7 — Final parity audit and release gate

## Outcome

Prove that v3.2 contains the complete approved client content while retaining the v3.1 design.

## Work

Run an adversarial final audit:

- Fetch/render all 20 authoritative URLs locally and on the deployed preview.
- Compare against the normalized corpus and matrix.
- Check every content row, not only headings.
- Check all nine areas and eleven services.
- Check desktop/mobile navigation.
- Check forms without submitting leads.
- Check metadata, sitemap, robots, links, images, and alt text.
- Capture screenshots for visual regression.
- Manually review exceptions; do not allow heuristic false passes.
- Confirm no unsupported content remains unless explicitly approved.

## Final gate

The release may be called v3.2 complete only if:

- Matrix has no unclassified critical rows.
- No material omissions remain.
- All intentional restructurings are documented.
- All unsupported additions are removed or approved.
- All automated and browser checks pass.
- Visual design remains the v3.1 direction.
- Deployment preview is verified against the same evidence.

### Queue prompt 7

```text
V3.2 STAGE 7 — Run the final adversarial parity and release audit.

Do not add new scope. Read docs/v3.2-content-parity-matrix.md and the client corpus. Verify the shipped local/deployed v3.2 site against every approved content row and every one of the 20 authoritative client URLs.

Check all page copy, headings, lists, services, service areas, FAQs, CTAs, contact facts, metadata, links, assets, alt text, navigation, mobile discoverability, forms, sitemap, robots, and canonical behavior. Use real browser paths for rendered content and structural checks for every route. Capture visual evidence at desktop and mobile widths.

Report PASS only if every critical row is exact or intentionally represented without loss, every intentional restructuring is documented, and no unsupported additions or omissions remain. Otherwise report FAIL with exact route/row gaps and continue fixing the smallest concrete gaps. Do not declare v3.2 complete from a passing heuristic alone.
```

Queue these in order, waiting for each stage's evidence/gate before releasing the next:

1. Prompt 0 — baseline
2. Prompt 1 — client content corpus
3. Prompt 2 — parity matrix
4. Prompt 3 — canonical data model
5. Prompt 4 — global navigation
6. Prompt 5A — home/about/contact/FAQs
7. Prompt 5B — core services
8. Prompt 5C — remaining services
9. Prompt 5D — service areas
10. Prompt 5E — galleries/assets/footer
11. Prompt 6 — forms/SEO/release
12. Prompt 7 — final audit

Do not queue all implementation prompts blindly if a previous stage produces unresolved source decisions. The queue can be prepared in advance, but execution must remain gate-controlled.

## What each prompt must leave behind

Every implementation prompt should finish with:

- Files changed
- Routes affected
- Tests run and results
- Build/type/lint status
- Browser/visual evidence where relevant
- Parity matrix rows updated
- Remaining gaps, if any
- Explicit statement that overall v3.2 is not complete until Stage 7 passes

## Failure handling

- If a stage fails due to a code issue: fix that stage and rerun its gate.
- If a stage reveals ambiguous client content: record it in `docs/v3.2-content-decisions.md`; do not invent a resolution.
- If live content changes during the mission: recapture the affected corpus and mark the matrix version/date.
- If deployment differs from local: treat the deployed preview as a release blocker until explained.
- If a heuristic parity script passes while manual content review finds omissions: the manual finding wins.
